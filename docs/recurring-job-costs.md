## 返信のコストを下げる手（2026-09-08 に整理）

> 起動回数はむしろ通過率を考えると増やしてほしい。
> ただし、その分 LLM のコストを下げる方法をあらゆる手段で考えて

### 前提として押さえる 2 つの事実

**① 出力は入力の 5 倍 高い。**

| Haiku 4.5 | |
| --- | --- |
| 入力 | $1.00 / MTok |
| **出力** | **$5.00 / MTok** |

**削るなら出力から。** いまの skip は 100 字超の日本語で理由を作文しており、
**いちばん高いトークンを説明文に使っている。**

```
"reason":"生成側が skip: 相手は投資判断の決め手について意見を求めているが、
アタシが「正解」を示すと責任が生じる。金銭判断への助言は避けるべき。また、
相手の投稿には具体的な失敗例・成功例・数字がなく、こちらから情報を足す根拠がない。
無理に返信すれば型になる"
```

**`skip:money_advice` の 1 語で足りる。**

**② プロンプトキャッシュは Haiku 4.5 では効かない（いまのサイズでは）。**

キャッシュの最低トークン数は**モデルごとに違い、世代順に単調ではない。**

| モデル | 最低 |
| --- | --- |
| Claude Opus 5 | 512 tok |
| Claude Sonnet 5 / Sonnet 4.6 | 1,024 tok |
| **Claude Haiku 4.5（いま使用中）** | **4,096 tok** |

いまのプロンプトは **約 3,168 tok**（2026-08-15 実測）。**足りない。**
`cache_control` を付けても **`cache_creation_input_tokens: 0` で静かに無効**になる。
**エラーは出ない。** 効いていると誤解しないこと。

**ただし「まとめ判定」で入力が 4,096 を超えると、キャッシュが使えるようになる。**
入力削減とキャッシュ解禁が同じ手で両立する。

出典: `claude-api` スキル `shared/prompt-caching.md`。**記憶で答えないこと。**

### 手の一覧（効く順）

| # | 手 | 仕組み | 効き |
| --- | --- | --- | --- |
| ① | **まとめ判定**（1 リクエストで 4〜8 件） | 固定プロンプトを N 回 送らず 1 回に | **入力 −70%**（推定） |
| ② | **skip の理由をコード化** | 出力単価は入力の 5 倍 | **出力 −70%**（推定） |
| ③ | **前段フィルタ強化** | hashtag のみ・短文・URL だけを **LLM を呼ぶ前に**落とす | 呼び出し −25% |
| ④ | `max_tokens` を絞る | 返信は 140 字 ≒ 100 tok | 暴走の上限 |
| ⑤ | 相手の投稿を切り詰める | 長文は先頭 N 字 | 入力 −数 % |
| ⑥ | Batch API | 50% 引き | **−50%**（鮮度とのトレードオフ） |

**順番が大事。** 先に単価を下げてから件数を増やす。逆だと高いまま倍になる。

### 16 件/日 は「通過率 100%」の前提だった（訂正）

**2026-09-06 に「16 件/日 = $1.44/月」と出したのは誤りだった。**
16 件 投稿 = LLM 16 回 と見ていたが、**実際の通過率は 25%** で、
16 件 出すには **約 43 回** 呼ぶ必要がある（残りは前段で $0）。

**約束の件数を出すコストは、私が言った額の 2.7 倍だった。先に言うべきだった。**

## 設計上の注意: 検知に LLM を使わない

15 分リプ自動化は「5 分ごとに対象アカウントの新規投稿を検知」する。
**この検知を LLM でやると、リプの件数と無関係にコストが乗る。**

| 方式 | LLM 呼び出し/日 | 1 か月あたり |
| --- | --- | --- |
| 検知も LLM（入力 2,000 tok × 288 回）※推定 | 288 | **$17.3** |
| 検知は API・スクレイピング、生成のみ LLM（5 件） | 5 | **$0.63** |

**桁が違う。** 検知は X API か取得済み HTML の突き合わせで行い、
**LLM は「実際に打つリプの文面生成」だけに使う。**
上段は推定（前提: 入力 2,000 tok・出力 0・Haiku）、下段は実測単価による計算。

フォロワーを増やす 4 つのループを `launchctl` に載せた。**実体で確認済み。**

**4 つとも LLM を呼ばない**ことを実機で確認した（SDK import 0 / CLI 起動 0 / API キー参照なし）。
DOM 操作だけなので、**稼働させても追加の API 費用は発生しない。**

| | 1 回あたり | 1 日あたり | 1 か月あたり |
| --- | --- | --- | --- |
| ①②③④ の追加費用 | $0 | $0 | **$0** |

### ① が間接的に増やしうる費用

`auto-thread-chainifier` 自体は LLM を持たない。「返信すべきエントリに印を付ける」役割で、
**実際の文面生成は既に稼働中の `incoming-reply-watcher` が行う。**

そのため ① を戻すと `incoming-reply-watcher` の実行件数が増えうるが、
**同ジョブの上限 20 件/日で頭打ち**になる。

| | 1 日 | 1 か月 |
| --- | --- | --- |
| 実績（1〜2 件/日） | $0.004〜0.008 | **$0.13〜0.25** |
| 上限に張り付いた場合（20 件/日） | $0.083 | **$2.50** |

**$2.50 は上限であって実績ではない。**

## 2026-09-06: 返信を 16 件/日 に増やした

利用者の指示（「1 日 8 件か 16 件だったよね？」→ **16 件/日**）で、
`comment-warmup` の `MAX_PICKS_PER_FIRE` を **2 → 4** に恒久変更した（plist を書き換え、
`unload` / `load` で反映）。**4 fires × 4 picks = 16 件/日。**

| | リプ/日 | 1 回 | 1 日 | 1 か月 |
| --- | --- | --- | --- | --- |
| 変更前 | 8 | $0.003 | $0.024 | $0.72 |
| **変更後** | **16** | $0.003 | **$0.048** | **$1.44** |
| 差分 | +8 | — | **+$0.024** | **+$0.72** |

**コストはちょうど 2 倍になる。** 入口で $0 のまま落ちる候補があるぶん、
実額はこれより下がる（実測では 8 件中 2 件が $0 で見送りだった）。
