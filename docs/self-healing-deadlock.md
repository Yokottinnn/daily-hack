# 自己修復の仕組みが、自己修復を妨げた（2026-09-08〜12）

X の返信・フォロー・アンフォローが **4 日 止まった。** 原因は 2 つだが、
**どちらも「安全のために作った仕組み」が引き起こしている。** 同じ型なので 1 本にまとめる。

> 返信・フォロー・アンフォロー／これが最重要タスクなので、
> 上記のタスクを絶対に止めないような体制を作って欲しい

## 型: 「治す／守る」仕組みが、治る道を塞ぐ

| | 仕組み | 善意の目的 | 実際に起きたこと |
| --- | --- | --- | --- |
| ① | `chrome-cdp-heal` | CDP が壊れたら Chrome を再起動して治す | **治せない状態**で 5〜6 分おきに Chrome を kill し続け、**利用者のブラウザを破壊した** |
| ② | `tab-guard` | 利用者がタブを一括で消したら自動化を止める | **CDP 断を「ウィンドウ全消え」と誤判定**し、`ai.openclaw.*` を全 unload。**Chrome を起動するジョブごと消した** |

### ② の悪循環（これが 4 日 の正体）

```
① CDP（自動化専用 Chrome）が落ちる
② tab-guard が「全消え」と誤判定 → ai.openclaw.* を全 unload
③ Chrome を起動するジョブも消える
④ → ① に戻る。永久に抜けられない
```

**`tab-guard` は CDP の `/json/list` でタブを数えている。**

```javascript
const req = http.get({ host:"127.0.0.1", port, path:"/json/list", ... })
req.on("error", () => resolve({ reachable: false }));
...
haltAutomation("Jordan の Chrome プロセスが消滅（ウィンドウ全消え）");
```

実ログ。

```
[2026-09-12T13:28:57Z] 🚨 Jordan の Chrome プロセスが消滅（ウィンドウ全消え） → 自動化を全停止
[2026-09-12T13:29:08Z] 🚨 同上
```

**「繋がらない」は「消された」ではない。** ここを同一視したのが設計の穴。

## 自動復旧を書くときの 4 条件

**「治す」「守る」仕組みを作るときは、次を全部 満たすこと。**

1. **治すために壊さない。**
   kill / 再起動を手段にするなら、**壊す対象が利用者の持ち物でないこと**を先に確かめる。
   `chrome-cdp-heal` は自動化専用 Chrome を再起動するつもりで、利用者のウィンドウを消した。

2. **失敗が続いたら自分を止める。**
   2 回 連続で目的を達成できなければ、**自分を unload する**か、実行を止める。
   `chrome-cdp-heal` は失敗し続けながら 5 分おきに動き、被害だけを積み上げた。

3. **自分が止める対象に「自分を復帰させうるもの」を入れない。**
   `tab-guard` は Chrome を起動するジョブを止めたので、**自分で自分の判定条件を
   永久に成立させ続けた。** 止める対象から復旧経路を除外する。

4. **「観測できない」と「異常」を区別する。**
   CDP に繋がらない ＝ 観測できない。**それは「タブが 0 枚」とは違う。**
   前回も観測できていなかったなら、**比較そのものを行わない。**

## 見えるようにしたもの（2026-09-12）

`scripts/ops-heartbeat.sh` に 4 項目を足した。**30 分ごとに `ops/heartbeat` へ出る。**

```json
"login_lock": {"present": true, "age_hours": 51},
"cdp":        {"healthy": false, "port": 18810},
"x_jobs":     {"loaded": 0, "expected": 8, "ai_total": 1, "halted": true, "missing": [...]},
"last_reply": {"at": "2026-09-09T...", "age_hours": 76, "stale": true}
```

**`last_reply` が唯一の「動いているか」の判定。** キューの `x_tweet_id` から取る一次情報で、
8 時間 出ていなければ `stale: true`。`x_jobs.halted` は tab-guard の非常ブレーキの署名。

## ③ ロックを書いていたのは tab-guard 自身だった（2026-09-13 に確定）

**`x29` は「このロックを作るコードは無い」と報告した。間違いだった。**

`x38` が**ロックの中身**を読んで決着した。

```
パス   : /tmp/x-login-in-progress
更新   : 2026-09-13 00:24:13
中身   : tab-guard
```

tab-guard のログの halt 時刻と**秒まで一致する。**

```
[2026-09-12T15:24:13.329Z] 🚨 Jordan のタブが 1 → 0 枚 → 自動化を全停止
                 ↑ 15:24:13Z ＝ JST 00:24:13
```

実体は `tab-guard.js` の 2 行に分かれていた。

```javascript
27: const LOCK = "/tmp/x-login-in-progress";
64:   try { fs.writeFileSync(LOCK, "tab-guard"); } catch {}
```

**`x29` はパスの文字列で grep したので 27 行目しか見えず、「書いている所は無い」と結論した。**

### だから grep は 2 手 打つ

| 手 | 何を打つか |
| --- | --- |
| 1 | **リテラル**（`x-login-in-progress`）で**定義**を見つける |
| 2 | **その定義名**（`LOCK`）で**使用**を見つける |

**1 手目だけで「無い」と言わない。** 定数に切り出されていれば、使用側にリテラルは出てこない。

同じ穴に 2 回 落ちた。`x39` のパッチは「`x-login-in-progress` と `writeFileSync` が
**同じ行にある**」条件で書いたため、**1 行も書き換わらなかった**（レポートに
「書き換え対象の行が見つからなかった」と出た）。`x40` で `writeFileSync(LOCK` に直した。

**ファイルを書き換えるときは、書き換え「前」と「後」の両方を grep で出す。**
`x39` は「後」を出していなかったので、当たっていないことに気づくのが 1 往復 遅れた。

## 私が診断を外した回数と、その理由

| 回 | 私の診断 | 実際 | なぜ外したか |
| --- | --- | --- | --- |
| 1 | `playwright` の cwd が違う | パッケージ名が **`playwright-core`** | **動いているスクリプトの `require` 行を読まなかった** |
| 2 | `command -v node` が v26 を拾う | v24 にも無い。同上 | 同上 |
| 3 | `chrome-cdp-heal` は症状 | **犯人だった**（利用者がスクショで特定） | ログを読む前に容疑者を並べた |
| 4 | `launchctl load -w` は載らない | **載る。直後に外される** | **載った瞬間だけ見て、60 秒後を見なかった** |
| 5 | 番人を `bootstrap` に直せば解決 | 的外れ。**外す主を止めないと無意味** | 上の誤診の上に重ねた |
| 6 | ロックを作るコードは無い（`x29`） | **tab-guard が書いていた** | **リテラルで grep しただけ。定数名で追わなかった** |
| 7 | ロックの書き込みを無効化した（`x39`） | **1 行も書き換わっていない** | **書き換え「後」を grep で出さなかった** |

**共通する失敗の仕方: 全文を読む前に、部分から原因を組み立てた。**

- `ensure-chrome.sh` の全文を読めば、`login-mode-guard` は **1 行**で分かった
- `tab-guard.js` の全文を読めば、CDP を見ていることは **1 行**で分かった
- 稼働中スクリプトの `require` 行を読めば、`playwright-core` は **1 行**で分かった
- **ロックの中身を 1 回 `cat` すれば、犯人は 1 語（`tab-guard`）で分かった**

**「読む」より先に「直す」を始めない。**

## まだ分かっていないこと（2026-09-13 01:30 時点）

**約 61 秒 周期で、ジョブが載っては消える。**

```
★ 01:27:28 消えた: comment-warmup
★ 01:28:29 消えた: comment-warmup   ← 一度 戻ってから、また消えている
★ 01:29:30 消えた: comment-warmup
```

**戻っている以上、載せている主も居る。** tab-guard のログはその間 1 行も増えていない。
`x40` で `log show --predicate 'subsystem == "com.apple.xpc.launchd"'` と
`StartInterval` の一覧から特定を試みている。

### ここで方針を変えた

**「載り続ける」ことを先に解こうとして 4 日 使った。**
**載り続けなくても、載った瞬間に走らせれば返信は出る。**

`x40` は launchd に載らなければ `comment-orchestrator.sh` を**直接 叩く。**
ジョブの常駐と、返信を出すことは、**別の問題として切り離す。**
