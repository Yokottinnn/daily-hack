# なぜ X 投稿が 2 時間 20 分かかって、それでも出なかったのか

2026-08-30 のサウナ告知。**承認（👍）は得ていた。画像も確定していた。それでも出なかった。**
最終的に利用者がスレッドの 2 投稿目を手で投稿した。

> 「なぜ30分にしてたの？理解できない。おれの時間を奪いたいの？」
> 「二度とやるつもりはないので、なぜここまで投稿が遅いのか原因を徹底的に分析して」

**これは「遅かった」話ではなく、「経路の設計を間違えていた」話である。**

## 1. 何が起きたか（JST）

| 時刻 | 出来事 | 結果 |
| --- | --- | --- |
| 21:43 | `t002` をマージ（**1 回目**） | |
| 22:13 | 周回が `t002` を実行 | ❌ **投稿されず** |
| 22:14 | `t003`（ハートビート 30 分 → 3 分）をマージ | **22:13 の周回を 49 秒差で逃す** |
| 22:25 | `t004` / `t005` をマージ（**2 回目**） | |
| 22:29 | `t003` を取り下げ | **自分を殺す設計だった**（後述） |
| 22:39 | Mac で手動実行 → `t004` | ❌ `"reason":"no candidate"` |
| 22:42 | `t005` | ⏸ [1/2] が無いので 3 分待って**正しく中止** |
| 23:54 | `t006` / `t007` をマージ（**3 回目**） | |
| 00:07 | **利用者が手で投稿。** `t006`/`t007` を取り下げ | 走る前に停止（二重投稿は無し） |

**1 回目のマージから 2 時間 20 分。3 回試して 0 回成功。**

## 2. 原因は 5 つ。うち 1 つが致命的

### 原因 1 ── 30 分ポーリングを「命令の経路」に使っていた（構造）

**そもそも、なぜ 30 分だったのか。**

`com.dailyhack.ops-heartbeat` は **2026-08-15 に「外部死活監視」として作られた。**
目的は GitHub Actions（`ops-watchdog.yml`）に対して
「Mac は生きている」と 30 分おきに示すこと。**死活監視として 30 分は妥当である。**

問題は、そのあと**これが「クラウド → Mac」の唯一の命令経路に転用された**こと。

```
死活監視（30 分で十分）  →  そのまま  →  命令の経路（30 分では話にならない）
```

**転用したときに間隔を見直さなかった。** 私はこの 30 分を所与のものとして受け取り、
痛い目を見るまで疑わなかった。**利用者の時間を奪う設計だと認識していなかった。**

### 原因 2 ── タスクは 1 回しか走らない（構造）

`scripts/ops-heartbeat.sh:162` は **rc に関係なく**実行済みの印を書く。

```bash
out="$(/bin/bash "$task_tmp/$t" 2>&1)"; rc=$?
printf '%s rc=%s\n' "$(date -u ...)" "$rc" > "$WT/done/$t"   # 成否を問わず必ず書く
```

つまり**失敗しても同じファイルは二度と走らない。** 直すには新しい名前で出し直すしかない。

```
失敗 → 原因を読む → 新ファイルを書く → PR → CI(約1分) → マージ → 最大30分待つ
                                                              ≒ 1 試行 35 分
```

**35 分 × 3 回 = 105 分。** ここに診断と執筆の時間が乗って 2 時間 20 分になった。

### 原因 3 ── 契約を調べずに書き、失敗を「調べる手段」にした（← **これが致命的**）

**3 回の失敗は、どれも「知らなかったから」ではない。「先に読まなかったから」である。**

| 回 | 外していたもの | 先に読めば分かったか |
| --- | --- | --- |
| `t002` | `node -e 'code' A B C` の argv は `slice(1)`（`slice(2)` にした） | **分かった** |
| `t002` | publisher は id ではなく **kind** を取る | **分かった**（`usage:` 行に書いてある） |
| `t004` | `kind` は `"thread"`、`id` は `blog-promo-` 始まり | **分かった**（ソース 6 行目のコメントに書いてある） |

3 回目の答えは、**publisher のファイル冒頭にそのまま書いてあった。**

```javascript
  6: *   kind = blog-promo (== thread + blog-promo- prefix)
136:        e.kind === "thread" &&
137:        (e.id || "").startsWith("blog-promo-") &&
```

`blog-promo` は **kind の名前ではなく「モード」の名前**だった。

**私は「積んで、走らせて、返ってきたエラーで学ぶ」をやった。**
それは手元の shell なら 3 秒で回るやり方であって、**遅延 30 分の経路でやってはいけない。**

> **30 分かかる経路を、REPL のように使った。** これが 2 時間の正体である。

### 原因 4 ── 唯一の短縮策（`t003`）が自壊設計だった

`t003` はハートビートを 3 分にするタスクだったが、`launchctl bootout` で
**自分を実行しているジョブごと再ロード**していた。タスクはそのジョブの子プロセスなので自殺になる。

| | 起きること |
| --- | --- |
| 自分 | `bootout` の行で SIGTERM。以降は走らない |
| `done/` の印 | 162 行目に到達せず**書かれない** |
| 後続タスク | ループごと死ぬので**1 つも走らない** |

印が付かないので**次の周回でも同じことが起き、永久に自殺し続ける**ところだった。
走る前に取り下げたが、**間隔短縮は実現しなかった。**
しかも `t003` は 22:14 に main へ入り、直前の周回 22:13 を **49 秒差**で逃していた。

### 原因 5 ── 即時実行の代替が 2 回とも失敗した

30 分を待たずに Mac へ届かせようとして、Mac 上に Claude セッションを 2 回立てた。

| 回 | 結果 |
| --- | --- |
| 22:39 | **5 時間のレート上限に到達**（23:10 リセット）。1 回は走ったが途中で停止 |
| 23:57 | **私の依頼を「不審な自動指示」と判断して自分で拒否**し、権限ダイアログでブロック |

2 回目は、そのセッションが「t006/t007 は origin/main に存在しない」とも述べていた
（実際には存在した）。**この経路は当てにできない。**

## 3. 対策

**A → B → C の順で効く。A だけでも t002 と t004 の失敗は両方消える。**

### 対策 A ── 契約をリポジトリに固定する（コスト $0・即日）

実測で確定した publisher / queue-manager の契約を
[`docs/x-publisher-contract.md`](x-publisher-contract.md) に書く。**次からは読むだけ。**

| 項目 | 確定値 | 根拠 |
| --- | --- | --- |
| `kind` | **`"thread"`** | `auto-x-publisher.js:136` |
| `id` | **`blog-promo-` で始める** | 同 `:137`、冒頭コメント `:6` |
| モード引数 | `node auto-x-publisher.js blog-promo` | `usage:` 行 |
| 承認不要な kind | `["comment", "reply"]` | `queue-manager.js:108` |
| 必須フィールド | `id, kind, text` | 同 `:145` |

**推測を 1 つも残さない。** 分かっていないもの（画像のフィールド名など）は
「未確定」と書き、**確定させるまで当て推量で埋めない。**

### 対策 B ── 新しい連携は「まず調べるタスク 1 本」から始める

`ops/tasks` に**投稿するタスクを書く前に、契約を dump するタスクを 1 本通す。**

```
✅ 正: 1 周回で契約を確定 → 正しい形で 1 回目に成功        = 2 周回
❌ 誤: いきなり投稿タスク → 失敗 → 失敗 → 失敗            = 3 周回 + 診断時間
```

**1 周回を投資して、以後の推測をゼロにする。** 今回はこれを省いて 3 周回を失った。

### 対策 C ── ハートビートを短くする（安全な再ロードで）

30 分 → 3 分にすると **1 試行 35 分 → 8 分。**

`t003` の自壊を繰り返さないため、**再ロードを自分の中でやらない。**

- 冒頭で「もう 180 秒になっているか」を見て、なっていれば**何もせず `exit 0`**
  （印が付いて、以後の周回に巻き添えを出さない）
- plist を書き換えるだけにして、**再ロードは別の一発ジョブに任せる**

### 対策 D ── 即時経路をつくる（本命。ここだけ設計判断が要る）

対策 C でも**最悪 3 分**は待つ。承認済みの投稿を出すのに 3 分待つ必要は本来ない。

| 案 | 遅延 | 実装 | 備考 |
| --- | --- | --- | --- |
| **D-1 軽量ポーラー**（別 LaunchAgent で `git fetch` だけを 1 分間隔） | 最大 1 分 | 小 | ハートビート本体と分離するので自壊しない |
| **D-2 `repository_dispatch`** を Mac が待つ | ほぼ即時 | 中 | 常駐プロセスの死活監視が別途要る |
| **D-3 Cloudflare Tunnel** で Mac に HTTPS 受け口 | 即時 | 大 | 最速だが公開面ができる。認証設計が要る |

**クラウドから Mac へは SSH で届かない**（ssh 未インストール・鍵なし・生 TCP 不可・
Mac は家庭内 NAT の内側。2026-08-30 に再実測）。**HTTPS だけが出られる。**

### 対策 E ── 承認から投稿までに締め切りを置く

今回、私は「次の周回で出ます」を**2 時間 20 分言い続けた。**

> **👍 から 30 分で出ていなければ、経路を疑って人に伝える。**
> 「次の周回で」を 2 回言ったら、それは経路が壊れている合図として扱う。

## 4. コスト

**ハートビートも `ops/tasks` も LLM を呼ばない。** `launchctl` の一覧、ログの mtime、
`git fetch` だけである。**これは推定ではなく、API 呼び出しが存在しないという構造的な事実。**

| 対象 | 1 回あたり | 1 日あたり | 1 か月あたり |
| --- | --- | --- | --- |
| ハートビート 30 分間隔（現状・48 回/日） | **$0** | **$0** | **$0** |
| ハートビート 3 分間隔（対策 C・480 回/日） | **$0** | **$0** | **$0** |
| 軽量ポーラー 1 分間隔（対策 D-1・1,440 回/日） | **$0** | **$0** | **$0** |

**回数を 30 倍にしても API 課金は増えない。** 増えるのは Mac の CPU 時間と
`git fetch` の通信だけである。

比較のため、**実際に課金が発生している**ジョブ（今回の変更で増減しない）。

| 運用 | リプ/日 | 1 回あたり | 1 日あたり | 1 か月あたり |
| --- | --- | --- | --- | --- |
| `comment-warmup`（2 picks・**実測**） | 8 | $0.00417 | $0.033 | **$1.00** |

単価の出典は `claude-api` スキルの料金表（Haiku 4.5 = $1.00/$5.00 per MTok）。
詳細は [`docs/recurring-job-costs.md`](recurring-job-costs.md)。

## 5. この文書の使い方

- 投稿タスクを書く前に **対策 A の表**（`docs/x-publisher-contract.md`）を読む
- `ops/tasks` の実行モデル（1 回しか走らない・名前順・自分を殺さない）は
  [`docs/ops-task-runner.md`](ops-task-runner.md)
- **「次の周回で」を 2 回言ったら、経路を疑う**
