# フォロワーを増やすための施策

## 現状の数字

| 項目 | 値 | 出典 |
| --- | --- | --- |
| フォロワー | 180 人 | 2026-07-21 の follower-snapshot |
| リプライ実施 | 8 件/日 | `comment-warmup` 4 fires × 2 picks（2026-08-15 に実機で確認） |
| Free tier のリプ上限 | 200 件/日 | 運用設計書 v3 |
| 上限に対する使用率 | **4%** | 上記より |

そして 2026-08-10 から 8/15 までの 5 日間、**すべてゼロだった**（Chrome 自動更新による全停止）。

### 「10 件/日」は机上の数字だった

この文書は当初 `5 fires × 2 picks = 10 件/日` を前提にしていたが、**実機と違っていた。**
2026-08-15 に plist を読んで判明した実効値は次のとおり。

| | 想定 | 実機（8/15 16:00 発火時点） |
| --- | --- | --- |
| 発火回数 | 5 回/日 | **4 回/日**（12/16/19/22 時） |
| 1 回あたり | 2 件 | **8 件**（`MAX_PICKS_PER_FIRE=8`） |
| 合計 | 10 件/日 | **32 件/日** |

16:00 の発火で実際に 8 件が X に投稿されたことで発覚した。投稿内容自体は正常
（アスカ口調・相手の投稿に具体的に言及・URL なし）だったが、量が想定の 4 倍だったため
`comment-warmup` を一時停止し、承認を得て `MAX_PICKS_PER_FIRE=2` に戻して再開した。
**現在の実効値は 4 fires × 2 picks = 8 件/日。**

数字を設計書に書いただけでは実機とは一致しない。**plist の実効値を読んで確かめること。**

## 最も効くテコが、唯一自動化されていない

運用設計書 v3 は、最も効く施策をこう書いている。

> 大手節約/ポイ活アカ (2-5kフォロワー) に投稿15分以内リプ 5件（Out-of-Network 露出最強テコ）

ところがこれは**「本日の手動タスク」に分類されている。** 自動化されていないため、
実行されたかどうかも記録に残らない。**自分たちで「最強」と判定した施策が、
唯一 人手依存のまま放置されている**という構造になっている。

ここを自動化するのが、いま最も費用対効果の高い一手である。

## なぜ 15 分以内なのか

X のタイムラインは、投稿直後のリプライほど上位に表示される。
フォロワー 2〜5k のアカウントの投稿に早期にリプを付けると、
**そのアカウントのフォロワー（＝自分をまだ知らない層）の目に触れる。**
これが Out-of-Network 露出であり、フォロワーが増える主経路になる。

逆に、投稿から時間が経つとリプは埋もれ、露出はほぼゼロになる。
**速度がそのまま効果を決める施策**なので、人手でやると効果が出ない。

## 設計

```text
5分ごと
  対象アカウントの新規投稿を検知
    → 投稿から15分以内か判定
      → リプライを生成（v3 ブランド準拠）
        → 投稿
          → 記録（どのリプがどのアカウントに対して打たれたか）
```

### 対象アカウントの条件

- フォロワー 2,000〜5,000 人。多すぎるとリプが埋もれ、少なすぎると露出が取れない
- 節約・ポイ活・家計といった、ブログの読者層と重なるジャンル
- 投稿頻度が高く、リプが付きやすいアカウント

**既存の `influencers.json`（7 件）は 1 件も条件に合わなかった。** 2026-08-15 に
フォロワー数を実測したところ、723〜104,000 とばらつき、2,000〜5,000 に収まるものが
無い上にジャンルも合わないものが混じっていた。そのため新規に探索し直し、
条件を満たす **8 件**を選び直している。

**手元にあるリストを条件に合っていると仮定しない。** 実測してから使う。

### 安全側の制約

自動リプライは X から spam と判定されうる。**量を急に上げない。**

| 制約 | 値 | 理由 |
| --- | --- | --- |
| 同一アカウントへの連投 | 1 日 1 回まで | 粘着と判定されるのを避ける |
| 開始時の総量 | 5 件/日 | 既存の 8 件/日 とは別枠。まず様子を見る |
| 増やす条件 | 1 週間 異常なし | フォロワー減・リプ削除・警告が出ていないこと |
| 上限 | 30 件/日 | Free tier 上限 200 に対して十分低く保つ |

**凍結したら全部止まる。** 上限に近づける価値より、止まらないことの価値が大きい。

### 中身の条件

- v3 ブランド準拠（マスコット＝ハッカー子 / 一人称＝アタシ）
- **相手の投稿内容に具体的に触れる。** 定型文はリプ削除やブロックを招く
- 自分のブログ URL は貼らない。**リプに URL を入れると露出が落ちる**（子リプライに回す方針と同じ）

## 実装状況

`~/.openclaw/workspace/scripts/quick-reply-watcher.js` として実装済み（安全制約をコードに固定、
`DRY_RUN=1` 対応）。**2026-08-15 の DRY_RUN 中に Mac 側セッションの OAuth が失効して中断し、
結果が未確認のまま。** バックグラウンドは exit 0 で終了しているので、
`~/.openclaw/workspace/logs/quick-reply-watcher.log` を読めば検証を再開できる。

**有効化はまだしていない。** 投稿せずに「検知・生成・15 分判定」が正しく動くことを
確かめてから、費用と凍結リスクを提示して承認を取る。

## 費用（2026-08-15 実測）

生成は Haiku 4.5（入力 $1/M・出力 $5/M）。`asuka-fill.js` が 37 テンプレを整形 JSON で
毎回全件送っていたのを 1 行 1 テンプレ形式に圧縮し、**入力を 40% 削減**した
（5,237 → 3,168 tok）。圧縮後も実生成で `ok:true / attempts:1 / weight:87`、
相手の投稿に具体的に言及する品質を保っている。

| | 1 リプ単価 |
| --- | --- |
| 軽量化前 | $0.00624 |
| 軽量化後 | **$0.00417** |

| 運用 | リプ/日 | 月額（軽量化後） |
| --- | --- | --- |
| 現状（4 fires × 2 picks） | 8 | $1.00 |
| **＋この施策（15 分リプ 5 件）** | 13 | **$1.63** |
| 参考: 8 picks のままだった場合 ＋ 15 分リプ | 37 | $4.63 |

CLAUDE.md のコスト方針（Haiku 運用分離で月 $6 → $0.41 にした経緯）に照らすと、
**8 picks のまま走らせるとその改善を帳消しにする水準**になる。量を戻さないこと。

## 効果の計測

**何が効いたか分からないまま量を増やさない。** リプごとに記録する。

| 記録項目 | 用途 |
| --- | --- |
| 対象アカウント / 投稿 URL | どの層に効くか |
| リプまでの経過時間 | 15 分以内の効果を検証する |
| リプ後 24h のフォロワー増減 | 帰属の手がかり |

既存の `follower-snapshot` が日次の増減を持っているため、
**リプの実施時刻と突き合わせれば粗い帰属は取れる。**
