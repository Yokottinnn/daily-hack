# ブラウザが 5 分おきに消された（2026-09-08）

利用者の Chrome が繰り返し消され、**最重要課題**として扱った事故の記録。

## 何が起きたか

Slack `#fun_reward-hack_tweet` に、この通知が 5〜6 分おきに出続けていた。

```
00:09 / 00:19 / 00:25 / 00:30 / 00:35 / 00:41
🚨 @Naoki Yokota Chrome CDP heal 失敗。SSH で 手動対応要
```

**`ai.openclaw.chrome-cdp-heal` が「CDP を治す」処理に失敗し続け、
そのたびに Chrome を落としていた。** 失敗するので何度でも繰り返す。

利用者が Slack のスクリーンショットを出して「完全にこれのせい」と指摘し、確定した。

## 止め方（1 行）

```bash
launchctl unload ~/Library/LaunchAgents/ai.openclaw.chrome-cdp-heal.plist
```

**利用者が自分で実行するのが最速だった。** 私は同じ操作を 3 経路で出そうとしていたが、
そのうち 2 つ（Mac セッションへのトリガー、GitHub 経由のタスク）は間に合っていない。

> CLAUDE.md「緊急依頼は 1 件だけ送る」の
> **「1 操作で済むことは、投げる前に自分でやるか依頼するかを選べるようにする」**
> がそのまま当てはまった。**最初にこの 1 行を出すべきだった。**

## 「治すジョブ」は、治せないとき破壊装置になる

これが今回の構造的な教訓。

- `chrome-cdp-heal` は **CDP が不健全なら Chrome を落として起動し直す**
- **その再起動が失敗する状態**だと、5 分おきに落とすだけの装置になる
- 落とされる側には**利用者が開いていたウィンドウ**が含まれる

`ensure-chrome.sh` には **cookie がディスクに永続化できておらず、再起動＝即ログアウト**
という但し書きがある（`t050`）。**Chrome が落ちること自体が、ログイン切れと投稿失敗に直結する。**

### 直すときの条件

**戻す前に、次のどれかを満たすこと。**

1. **連続失敗したら自分を止める。** 2 回 続けて失敗したら unload する
2. **利用者のウィンドウを巻き込まない。** 落とすのは CDP 用のプロファイルだけにする
3. **落とす前に必ず通知する。** 事後ではなく事前

**「失敗しました」を 5 分おきに投げ続けるのは、通知ではなく騒音。**

## 前科

2026-08-30 23:57:03 JST に **タブが 19 → 1 枚**になっている（`t014` / `t015`）。
当時 uptime 20 日で **OS の再起動ではなかった**。`tab-guard` が検知して自動化を全停止した。

**そのときも「消した本体」は特定できていなかった。** 今回の犯人と同一かは未確認。

## 残っている根本原因

**`chrome-cdp-heal` は症状であって原因ではない。** 「CDP が不健全」と判断したから動いた。

- `x16`（2026-09-08 00:18）で **`trend-detect.js` が CDP 経由でハング**し、
  120 秒で打ち切られている（rc=137）
- heal を止めたので、**壊れた CDP を自動で直すものが無くなった**。
  投稿や返信が失敗し始める可能性がある
