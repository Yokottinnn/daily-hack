> 元にした資料は利用者が渡した運用マニュアル（PDF 50 ページ・公式資料の確認日 2026-09-27）。**原本の全文の写しは非公開の `Yokottinnn/daily-hack-affiliate` の `docs/playbook/claude-affiliate-manual.md`**。このスキルは daily-hack の運用に合わせて書き直したもの（公開リポジトリなので原文は貼らない）。

**このスキルは blog-article の代わりではない。** 画像・検査・公開の手順は blog-article のまま。このスキルは「何の案件を、誰に、どの判断材料で、どう届けて、どう直すか」を決める。

## 0. 考え方（全部の前提）

- **収益の流れは 4 段: 悩みのある読者（X・検索）→ 判断材料（記事）→ 本人が選ぶ（公式の窓口・店）→ 条件を満たして成果確定 → 入金。** 紹介者の価値は「申し込む前の分からないことを減らし、向いている人・向かない人を説明すること」。不要な申込を促すほど信頼も成果の質も下がる
- **小さく 1 本ずつ組み立てる。** 最初から 4 案件を並行させない。1 案件で「案件カード → 記事 → 告知 → 記録」を通してから次へ
- **頑張る量ではなく、1 度作ったものが何度も効く形を先に作る。** 毎回ゼロから書かない。このスキル・案件カード・根拠台帳・告知の型を使い回す
- **数字は仮定と実績を分ける。** 収益の試算は「確定件数」に置き換えて考える（下の 1-3）。月◯万円を保証する書き方はしない
- **「予約・申込」と「着金」は別の段階**（申込 → 成果発生 → 成果確定 → 報酬支払）。記録も分ける

## 1. 案件を選ぶ

### 1-1. 選ぶ質問は 3 つ
1. 買う・申し込む前の迷いを、自分たちが説明できるか
2. 公式情報を読み続けられるか（条件が変わったら追えるか）
3. デメリット・向かない人も伝えられるか

### 1-2. 必須条件（点数より先）
- [ ] 対象者と無料の範囲が公式情報で確認できた
- [ ] 成果地点と主な否認条件を説明できる
- [ ] 掲載先・集客元・広告表現の条件を満たせる（A8 は SNS の個別メッセージ・PDF への広告掲載は不可）
- [ ] 現在の提携状態とリンクの使用条件が分かる（作戦室「ASP と案件」・`reports/board/asp-probe/a8partnered.json`）

成果地点か媒体条件が不明な候補は **保留**。必須条件を満たしたものの中から、少ない作業で説明を完成できる 1 件を選ぶ。点数（経験・読者理解・説明材料・更新しやすさを各 0〜2 点）は整理用で、高得点だから売れるとは限らない。

### 1-3. 目標を確定件数に分ける
- 月の目標額 ÷ 1 件の確定報酬 ＝ 必要な確定件数 → ÷ 確定率 ＝ 発生件数 → ÷ 発生率 ＝ 広告クリック → ÷ 広告クリック率 ＝ 記事の閲覧
- 作戦室「現状の数字 › アフィリエイト › 記事をあと何本増やせばよいか」の計算欄で、実績と仮定を分けて出す
- **単価の高さだけで選ばない。** 同じ単価でも成果条件と読者の合い方で必要な集客は変わる
- daily-hack の実績では 1 記事の月の読者が少ない（2026-10-31 で中央値 約 5 人）。**1 件の報酬が大きい無料相談・無料登録型（数千〜数万円）と、読者の多い記事の組み合わせが効く**。楽天・Amazon の物販（2〜10%）は数で補う

### 1-4. 案件カード（1 件につき 1 枚）
作戦室の「アフィ記事の作り方 › 案件カード」と `docs/affiliate-playbook.md` に同じ欄で残す。**空欄は「確認済み」の意味にしない。未確認・対象外・確認済みを分ける。** 契約上非公開の情報（管理画面だけの条件など）は内部の記録に限り、記事・外部 AI に貼らない。

| 欄 | 書くこと |
| --- | --- |
| 案件・確認日 | 案件名／確認日／公式 URL と資料の置き場 |
| 読者・対象条件 | 誰が対象か（年齢・地域・新規のみ等）。不明は「未確認」 |
| 読者の負担 | 無料の範囲／その後の有料部分 |
| 報酬・成果地点 | 報酬額／何をしたら成果か（申込完了・面談実施・開通など） |
| 期限・否認条件 | 申込後◯日以内／重複・取消・いたずら・本人申込 |
| 媒体・表現 | 許可される媒体、禁止の訴求、素材の条件、広告表記 |
| 承認・支払 | 提携状態、確定までの目安、支払条件 |
| 次の確認 | 不明点・問い合わせ先・再確認日 |

### 1-5. 否認条件を記事に反映する
| 案件の条件 | 記事でやること |
| --- | --- |
| 新規利用者のみ | 既存利用者向けの案内と混ぜない |
| 対象エリア・属性 | 読者が対象か判断できる確認先を示す |
| 申込後の実施期限 | 面談・体験の流れを確認した範囲で書く |
| 重複・虚偽・いたずら | 報酬目的の申込・代理申込を勧めない |
| 特典・インセンティブの制限 | 独自の景品を付けて申込を頼まない |
| 掲載禁止の媒体・表現 | 使えない導線と文言を最初に除く |

不明な条件は ASP が指定する窓口で問い合わせる（ひな型: 掲載予定の媒体の URL・読者・紹介内容・集客元・不明な条件・具体的な掲載方法を書いて、最新の適用条件を聞く）。広告主への無断の直接交渉はしない。

### 1-6. 提携まで（ASP）
媒体のテーマを 1 文にする → 公式サイトから登録 → 条件に合う候補を 3 件だけ探す → 掲載先 URL と読者像を添えて提携申請（実績が無ければ作らずそのまま書く）→ 承認後に**公式の方法でリンクを作り、公開前に遷移先を確かめる**（3 店ボタンの Amazon で、Claude が自分で作ったリンクを確かめずに出した 2026-10-30 の反省）。承認前に広告を載せない。

**もしもアフィリエイトは使わない**（2026-11-02 利用者の指示「もしもアフィリエイトはもう無視して…記事の中にバナーを掲載したりリンクを載せたりしないように」）。もしもの案件は候補にも挙げず、提携申請もしない。CI（test-build の「No moshimo links」）が、出来上がったサイトにもしものリンクがあればビルドを落とす。

## 2. 記事を作る

### 2-1. 読者は「申し込む直前の 1 人」
「30 代におすすめ」では何を書くか決まらない。生活場面・すでに試したこと・まだ分からないことまで具体化する。次の 4 つを書いてから構成に入る。
1. 読者が困っている場面は？
2. すでに自分で試したことは？
3. 申し込む・買う前に知りたい 3 つのことは？
4. 今回は対象にしない人・答えないことは？

**記事の約束を 1 文にする**（例:「初めて◯◯を考える人が、準備・流れ・向いている人を確認できる記事」）。読み終わって何を判断できるかを約束する。3 店ボタンの比較記事の「買う前の不安を 1 つ決めて、それで並べる」（`docs/shop-comparison.md`）と同じ考え。

### 2-2. 疑問を絞る
読者が申し込む前に知りたい疑問を 10 個出し、**最初の記事で答える 3 つ**を選ぶ（選んだ理由・必要な根拠・未確認の事項を書く）。自分たちの記録にある疑問と、AI が想定した疑問を分ける。検索数や申込率は資料が無ければ出さない。案件の対象外の人へ申込を勧める案は作らない。

### 2-3. 根拠台帳（体験と公式情報を同じ箱に混ぜない）
| 種類 | 記録する内容 | 公開するときの書き方 |
| --- | --- | --- |
| 公式の事実 | URL・確認日・該当箇所 | 「公式案内では…」 |
| 自分の体験 | 利用日・場面・感じたこと | 「アタシの場合は…」（ハッカー子の口調） |
| 読者の声 | 掲載許可・発言の範囲 | 出典と文脈を添える |
| 仮説・解釈 | そう考えた理由 | 「…と考えられる」 |
| 未確認 | 調べる相手と期限 | 確認できるまで断定しない |

**未利用なら調査型の記事にする。** 架空の面談・失敗談・担当者の発言は作らない。「使う前に調べたこと」「比べて分かった選び方」として調査の価値を届ける。台帳は記事ごとに `docs/research/`（affiliate）か記事の references に残す。

### 2-4. 構成（この順で書く）
1. PR 表記（`isPR: true` と冒頭の表示。消費者庁のステマ規制）
2. 誰の、何の迷いに答える記事か
3. 合いそうな人／合わなそうな人
4. 疑問 3 つへの回答（根拠を対応づける）
5. 利用の流れと、事前に確認したい注意点
6. 公式の対象条件を確認するための短い案内（ここで成果リンク・3 店ボタン）

daily-hack の型（冒頭の「読者の疑問 2 つ → 検索しても出てこない → だから作った」、比較表、1 対象 1 節、関連記事 2 か所）は blog-article のまま。上の 6 段はその中の「アフィリエイトの部分」の骨組み。

### 2-5. 書くときのルール
- 渡した体験以外を作らない。未利用なら調査型
- 不明な料金・所要時間・効果は「要確認」
- 「絶対」「誰でも」「相談だけで人生が変わる」は使わない
- 「相談無料」と、その後の有料契約を混同しない
- 金融・保険などの個別判断を代行する助言はしない
- 記事から LINE へは、利用条件の確認なしに誘導しない（daily-hack は LINE を使っていない）
- 出力するもの: 見出し付き全文／体験を足せる 3 か所／公開前に確認する主張の一覧（主張・出典・未確認点）

### 2-6. 公開前に文章を磨く
| そのまま出さない | 確認して書く形 |
| --- | --- |
| 予約するだけで報酬が入る | 成果条件を満たし、承認後に報酬となる |
| 絶対に◯◯できる | 対象者・支援内容・確認できた対応範囲を説明する |
| 無料だから何も失わない | 無料の範囲・必要な時間・登録情報を説明する |
| 誰でも月◯万円 | 試算の単価・件数・費用を分けて示す |
| 使って人生が変わった | 本人の記録がある事実と感想だけを書く |
| この保険・投資が一番いい | 個別の推奨を避け、公式の相談対象と確認項目を示す |
| 今だけ。残り◯名 | 根拠と期限を確認できなければ削除する |

- [ ] 広告と分かる表示が、記事・告知の見やすい場所にある
- [ ] 対象者・無料の範囲・注意点・出典が揃っている
- [ ] リンク先が説明した内容と一致し、規約上使える媒体である（**遷移先を実物で確かめる**）

## 3. 読者に届ける（X・tweet2 の担当）

- **プロフィール**: 誰の・どの悩みに答える発信かを書く。実績の数字より扱うテーマと提供する情報。「広告を含みます」
- **固定投稿**: 最初に読む記事を 1 つ案内する。記事にある 3 つの判断材料を並べ、読む理由を作る。PR 表記
- **1 記事から告知 30 本の候補を作る**（悩みの言語化 6・準備 6・選び方/比較 6・よくある疑問 6・実体験か調査で分かったこと 6）。各 130 字前後で判断材料を 1 つ、「記事を読むと何が分かるか」を最後に、PR 表記。本文に無い体験・効果・実績・数字を足さない。同じ意味の言い換えで数を増やさない。不安を煽らない・申込を強要しない
- **30 本は 30 回の検証候補。** 一度に予約せず、数本ずつ出して反応を見る。期限・条件・記事が変わったら予約中の投稿も直す
- 記事リンクは読みたい内容に直接つながるものにする（説明なく別ジャンルへ送らない）
- X の投稿の可否・文面は tweet2 の手順（x-post-copy）と daily-hack の最上位ルールが優先

## 4. 接点（LINE・7 回の整理ガイド）

- **daily-hack は LINE 公式アカウントで第三者のアフィ広告を配信しない**（LINE の規約で第三者の広告媒体としての利用が禁止、A8 も SNS の個別メッセージ・PDF への広告掲載を認めていない）
- 「7 回で判断材料を揃える」型は、**公開記事のシリーズ**として使える（登録直後〜6 日後の 7 回＝悩みを 1 つにする・優先順位・準備・比較の基準・質問を 3 つに・振り返りと次の行動）。各記事に前後の案内を付け、読者が必要な回へ直接移れるようにする。シリーズにアフィ広告を足すのは、承認された公開媒体（記事）の中だけ

## 5. 数字で育てる（affiliate の担当）

### 5-1. 途中の数字も残す
| 記録欄 | 見ること |
| --- | --- |
| 期間・案件 ID・記事 ID・投稿 ID | どの内容から来た反応かを追える |
| 投稿の表示・リンククリック | 読者に届き、記事に進んだか |
| 記事の閲覧・広告クリック | 記事が次の判断に役立ったか（計測方法も記録） |
| 発生・承認・否認・未確定 | 発生後の状態と、確定までの時間 |
| 確定額・入金額・経費・作業時間 | 売上と資金繰り、運用の負担 |

同じ期間・同じ定義の数字で比べる。取れない項目は「不明」。個人を識別する情報は分析に渡さない。daily-hack では作戦室「現状の数字」（成果は `results/latest`・記事は snapshot）がこの表。**数字は公開リポジトリに書かない。**

### 5-2. 来週直すのは 1 か所だけ
週次の分析で、①データから確かめられること ②母数や計測の違いで判断できないこと ③改善の仮説 1 つと根拠 ④次に変える箇所 1 つ ⑤変えたあとに見る数字・期間・保留条件、を出す。少数の成果から原因を断定しない。未確定を失敗に含めない。複数の箇所を同時に変えない。データ不足なら変えずに記録を続ける。
- 表示はあるが記事クリックが少ない → 告知で「何が分かるか」を具体化
- 広告クリックはあるが発生しない → 対象読者と公式条件の一致を再確認

### 5-3. 承認率は同じ発生月で比べる
今月の承認件数 ÷ 今月の発生件数 は別の月が混ざる。発生月ごとに後日どう確定したかを追う。未確定は否認に含めない。入金予定日と実際の入金日を分け、未確定の報酬を先取りしない。

### 5-4. 週の運用と、次の案件へ進む条件
| 曜日 | 作業 |
| --- | --- |
| 月 | 案件条件・終了通知・先週の数字を確認（affiliate の毎朝の定例と ASP の自動読み取り） |
| 火 | 読者の疑問を 1 つ補う記事更新（blog3） |
| 水 | 告知候補を作り、数本を確認して公開（tweet2） |
| 木 | 未確認事項・問い合わせ・リンクを整理（affiliate） |
| 金 | 週次分析と、来週の変更箇所を 1 つ決める（affiliate → 作戦室） |

2 案件目に進む条件: 1 案件目の記事と導線が完成し条件の変更を追える／発生から確定までを記録できる／読者の反応から改善の理由を説明できる／既存記事を更新する時間を残せる。**広げる単位は「隣の悩み」**（同じ読者の別の疑問を先に掘る）。

### 5-5. 最初の 30 日
前半（1〜15 日）は 1 本を完成させる: 読者設定 → 掲載先と ASP の条件を確認 → 候補 3 件を案件カードに → 媒体条件が合う 1 件へ提携申請 → 公式資料と体験を根拠台帳に → 疑問 3 つと構成 → 下書きと事実・表現の確認 → 承認と掲載条件を確認して公開。
後半（16〜30 日）は届けて直す: プロフィールと固定投稿 → 告知 30 本の候補 → 数本ずつ公開して記録 → 読者の疑問を記事に 1 つ足す → 7 回分のガイド（公開記事のシリーズ）→ 発生・承認・未確定を照合 → 週次分析と翌月の作業。
初月の目標は「公開と計測ができる状態」。未確定・少数データだけで案件の良し悪しを決めない。

## 6. 公式資料（条件を確かめる先）

A8.net の「収益発生までの流れ」「成果条件とは」「禁止事項」「PR 表記と掲載 URL」「SNS ガイドライン」「DM へのリンク送信」、LINE 公式アカウントのガイドラインとステップ配信のマニュアル、消費者庁のステルスマーケティングの資料。daily-hack では楽天アフィリエイトのガイドライン（https://affiliate.rakuten.co.jp/guideline/rule/ ）、Amazon アソシエイトの運営規約と紹介料率表、バリューコマースの LinkSwitch の条件も同じ扱い。**確認日・参照ページ・変わった条件・影響する記事と投稿を記録し、条件が変わったら既存記事と予約投稿にも反映する。**
